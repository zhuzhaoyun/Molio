WorkBuddy + Obsidian 装好之后，知识库里到底放什么

2026-10-08知识管理

先给结论：这套组合里，工具和接入都不难，难的是第三件事。你把 WorkBuddy 接上 Obsidian 之后，第一次问它一个你专业领域的具体问题，多半会得到一段四平八稳、说不上哪里错、但就是没有细节的回答。

问题不在工具，也不在模型。在于库里装的东西。

这套组合的分工

Obsidian 管的是“存在哪”：一堆 Markdown 文件放在你自己的硬盘上，用双链连起来，格式是开放的，十年后换个工具也能打开。

WorkBuddy 管的是“让 AI 读得到”：它是一个本地优先的个人 agent 运行时，建立在 Claude Code 与 Obsidian 之上，让 AI 能在你的本地文件上工作，而不是把资料上传到别处。

两者接起来之后，你会有一个能读你电脑上文件的 AI。这一步本身没有门槛，两边都有现成的文档。

装好之后撞上的那个问题

假设你已经接好了。现在你问它：“我们这行的 XX 规范里，这种情况该怎么判？”

它答了，条理清楚，但你就是不敢直接用。你去核对，发现它对了两处、含糊了一处、错了一处。你把资料再喂进去一些，好一点，有限。

这个体验很多人都碰到过，而直觉通常指向错的改进方向。 大多数人会去调检索：换分块策略、换 embedding、加重排。有效，但有限。

因为问题多半不在检索。一堆没有结构的文档，检索得再准也只是找到段落，不是找到知识。 模型拿到的还是碎片，它自然只能给你碎片级别的回答。

具体的表现是三种：

第一，它答不出“没写下来但逻辑上必然”的关联。 你的资料里写了 A 是某类，也写了 B 属于 A，但它不一定能替你推出 B 也应当满足 A 的约束。

第二，它分不清同名不同物的东西。 你单位说的“项目”和规范里说的“项目”不是一回事，但两边都写成“项目”。

第三，它给不出出处。 它说得像那么回事，但你没法核。而不敢核的答案，在专业场合等于没有答案。

内容层的三条来路

到这个位置，问题已经从“用什么工具”变成了“里面放什么”。可选的路其实只有三条。

第一条，自己从零整理。 最贴合你的需求，也最贵。贵不在动手，在于你得先把领域的结构想清楚：哪些是实体、哪些是概念、哪些是容易混的对照，然后逐条建页、建关系、逐段核引文。这件事本身是有方法的，但确实要投入时间。

第二条，把已有的文档堆进去。 最省事，但这就是前面说的那种体验的来源。文档是给人读的，不是给机器算的，堆得再多，结构还是零。

第三条，从现成的结构化知识底座起步。 把某个领域已经整理好的条目拿过来，当作骨架，再往上长你自己的东西。

第三条路适合的情况很具体：你需要的那个领域，恰好有人已经整理过，而且整理的质量你能核。

现成的知识底座长什么样

以 Molio（墨流）的知识工程全景图谱为例，它处理的正是“怎么把资料变成机器可用的知识”这件事本身：本体建模、Palantir 的多要素结构、RAG 与 GraphRAG、Agent 工程，整理成互相链接的结构化条目。

它是 Markdown 格式的本地文件夹，所以能直接放进上面那套组合里：Obsidian 能打开它，Claude Code、Codex 这类 Agent 也能直接读它。

需要说清楚它的边界：它是知识资料，不是可运行的程序，也不含 AI 调用服务。它替代不了上面任何一步，它只是让内容层不必从零开始。

常见问题

WorkBuddy 和 Obsidian 是什么关系？

Obsidian 是本地 Markdown 笔记工具，管“存在哪”；WorkBuddy 是一个本地优先的个人 agent 运行时，建立在 Claude Code 与 Obsidian 之上，管“让 AI 读得到”。两者是分工关系，不是替代关系。

装好之后为什么还是查不到东西？

因为瓶颈从工具转到了内容。一堆没有结构的文档，检索得再准也只是找到段落。要答“这两者什么关系”“这件事牵涉哪些人”这类问题，需要的是整理过的关系，不是更多的文档。

自己整理知识库和用现成底座，怎么选？

看两件事：你需要的领域有没有人认真整理过，以及你能不能核。自己整理最贴合需求但最贵；现成底座省掉从零建结构的成本，代价是要接受别人的分类方式。

现成知识底座能直接喂给 AI 吗？

能。它们是 Markdown 格式的本地文件夹，放进你自己的环境后，能读本地文件的 Agent 都能读它。数据全程在你自己电脑上，不需要上传，也不需要注册任何服务。

通用大模型已经知道很多了，还需要这些吗？

通用模型给的是凭训练记忆的概括，细节容易串，而且它指不出依据。在专业场合，“说得像那么回事”和“有出处可核”是两回事。
