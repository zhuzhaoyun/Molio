## 1. 背景与目标

图谱用 Sigma.js v3 (WebGL) 渲染，d3-force 做力导向布局，参考 Obsidian Graph View 的手感。
拖拽节点期望达成的目标（用户视角，也是验收标准）：

- **W1** 空闲时图谱被合理地 fit 在视野中（首次加载 / ML 重布局 / 筛选 / 重建时 auto-fit）。
- **W2** 按下节点瞬间，视图**不能**有任何瞬时跳变。
- **W3** 拖拽中：被拖节点**精确跟手**；其余节点可呈现 Obsidian 式「液体填补」流体效果；但**整张图必须留在视野中央**，不能整体平移滑走，也不能逐帧抖动；minimap 的世界框与视口框稳定、与主视图一致。
- **W4** 松手瞬间与松手后：不能跳变、不能继续漂移；孤立节点回到规整外围圆环（不飞散）。
- **W5** 单击（不拖）：选中节点，视图不动。
- **W6** 空白处拖拽 / 滚轮：交给 Sigma 原生画布平移 / 缩放（用户主动导航）。
- **W7** 优先级（用户明确）：**稳定是根基**（硬约束）；**流体效果是要保留的关键能力**（对齐 Obsidian 的体验核心，不能为稳定而砍掉）。

> W7 是本次最关键的约束：它排除了「最省事但会废掉流体」的方案，决定了最终走「保留全流动 + 加质心约束」这条路（见 §6.0）。

## 2. 必须先建立的心智模型（背后原理的根基）

不理解这个模型，就只能在表层打地鼠。屏幕上每个节点的像素位置由两层变换决定：

```
screenPos = matrix(camera.x, camera.y, camera.ratio, camera.angle)  ∘  normalizationFunction(graphPos)
```

- `normalizationFunction` 把**图坐标**映射到 [0,1] 的「framed」方块，参数是包围盒的**中心 (dX,dY)** 与**跨度 ratio**。
- 它由 `createNormalizationFunction(customBBox || nodeExtent)` 构造（sigma 3.0.3 源码）。
- `getGraphDimensions()`（喂给渲染矩阵）同样 = `customBBox || nodeExtent` 的跨度。
- `nodeExtent` 是**实时**包围盒，在每次 `process()` 里被重算为 `graphExtent(graph)`；而 `process()` 在每次带 `needToProcess` 的渲染（即每次 tick / 每次改图属性的 refresh）都会跑。

由此推出**视图发生变化的唯一两个来源**：

| 来源 | 含义 | 由谁触发 |
|---|---|---|
| **(C) 相机 state 变** | x/y/ratio/angle 改变 | 用户平移/缩放、相机动画、惯性 |
| **(N) 归一化基准变** | `customBBox || nodeExtent` 改变 | 节点位置变 → `nodeExtent` 变 → 在 `customBBox` 为空时每帧重算 |

> 关键 gotcha（源码确认）：`getBBox()` **只返回实时 `nodeExtent`，完全无视 `customBBox`**；
> 只有 `getCustomBBox()` 才返回 `customBBox`。而 `normalizationFunction` / `getGraphDimensions` 用的是 `customBBox || nodeExtent`。
> 这条差异是中间某一轮 minimap 出错的直接原因（见 §4 第 3 轮）。

另一个 sigma 事实：3.0.3 里 `autoCenter` **并不**用于在 `process()` 时重置相机（它只是 captor 的一个平移约束设置）。
所以「拖拽时视图乱跳」**不是相机被重置**，而是**归一化基准每帧重算**——相机 state 没动，但映射基准动了，于是整张图在固定相机下逐帧错位。

d3-force 侧需要知道的：

- 节点带 `fx/fy` 时被钉住（每 tick 末尾 `x=fx`）。
- `forceCenter(tx,ty)` 每 tick 把所有节点平移使**均值→target**；但若某节点带 `fx`，它收到的平移会被末尾的 `x=fx` 覆盖，于是误差每 tick 乘约 `1/N` 收敛——**节点越多收敛越快、残差越小**（密集图趋近 0，4 节点图约 1~2px，见 §7）。
- `forceX/forceY`（向心，强度随 degree）提供向 0 的拉力，但**挡不住**「被拖节点钉在远处 + 链接力」把整簇质心拽走——这正是需要 `forceCenter` 的原因。

## 3. 用户侧现象的演进（前因后果）

按用户反馈的时间顺序：

1. **拖拽时相机视角频繁切换、混乱不稳定**（逐帧跳）。
2. **好一点了，但 mousemove / mouseup 仍有漂移**，且 minimap 里相机视口框在变。
3. **拖拽时 minimap 从「满框」变成「缩成中心小团 + 角落几个飞点」**（图一 vs 图二）。
4. **按下瞬间会发生瞬时偏移**（第二次起每次拖/点都跳一下）。
5. **不再瞬移，但拖拽时整簇缓慢连续偏移**，滑到 minimap 边缘、半数节点出框。

每一轮我都修了「当时能看到的那一层」，却总冒出下一层——典型的地鼠式返工。根因见 §5。

## 4. 中间过程：逐轮尝试、为何只部分有效、又暴露了什么

> 诚实记录弯路，因为「为什么错」比「怎么对」更能防止复发。前 4 轮全部在**相机侧**打转，没碰**节点侧质心平移**这个真正的另一半根因。

### 第 1 轮：冻结归一化（治「逐帧跳」）
- **现象根因**：拖拽 `wake` 让全图流动，`customBBox` 为空 → `normalizationFunction` 每 tick 用实时包围盒重算 → 相机没动但映射在变 → 逐帧跳。
- **历史残留**：之前只用 `setSetting('autoRescale', false)`，它只把 `process()` 里的跨度强制成视口常量（冻住**缩放轴**），但**中心 dX/dY 仍跟实时质心走**，所以水平/竖直跳还在。
- **做法**：`setCustomBBox(...)` 冻结归一化基准——`normalizationFunction` 与 `getGraphDimensions` 都改用冻结值，两轴一起冻住。主画布逐帧跳消除。
- **遗留**：只解决了「映射每帧重算」，没解决「映射基准在按下/松手被切换」与「节点质心平移」。

### 第 2 轮：松手 refit 跳 + 孤立节点飞散
- **现象根因 A**：松手时清除 `customBBox` + 恢复 `autoRescale` → sigma 对**移动后的新包围盒**重新 fit → 相机被重新居中/缩放 → 松手跳。
- **现象根因 B**：`tileIsolatedNodes(graph)` 只写 graphology 属性、**不碰 d3 模拟节点**；mousedown「全流动」已把 d3 的 `fx/fy` 全解锁成 null，于是 `wake` 后首个 d3 tick 用拖拽末位的旧坐标覆盖平铺结果、且无约束 → 孤立节点被排斥力甩飞 → 包围盒撑大。
- **做法**：新增 `syncIsolatedToSim()` 把平铺位置/固定同步回 d3 handle；松手**不 refit**（先尝试「延迟 900ms 解冻」）。
- **遗留**：延迟解冻本身又在松手 ~0.9s 后制造一次重算跳；且 minimap 的「缩成小团」仍未解决。

### 第 3 轮：minimap 用错 API + 按下重捕获跳
- **现象根因 A（minimap 缩成小团）**：上一轮让 minimap 改用 `sigma.getBBox()`，但 **`getBBox()` 只返回实时 `nodeExtent`、无视 `customBBox`**（§2 的 gotcha）。拖拽时甩飞/流动的节点撑大实时包围盒 → minimap 世界框被撑大 → 中心簇缩成小团 + 角落飞点。主画布其实一直用冻结的 `customBBox`，是稳的——**前几轮用户在主画布感知的「漂移」，很大一部分是这个 minimap 实时框在变、被读成了相机在动**。
- **做法 A**：minimap 世界框改 `getCustomBBox() ?? getBBox()`，与主相机归一化**同源**。
- **现象根因 B（按下瞬移）**：mousedown 写的是 `setCustomBBox(null)` + `setCustomBBox(getBBox())` = **每次按下都重捕获实时包围盒**。但松手后 `customBBox` 持久保留，空闲相机是按**上一次**冻结基准 `E_prev` 取景的，而实时包围盒已沉降到 `E_idle`（≠`E_prev`）；重捕获把基准从 `E_prev` 切成 `E_idle` → 相机没动但映射变了 → **按下那一帧整图跳**（第二次起每次拖/点都跳）。
- **做法 B**：mousedown 改为「冻结到相机当前正在用的基准」——`if (!getCustomBBox()) setCustomBBox(getBBox())`；已有冻结则**不动**（它本就是当前视图基准，零跳变）。单击分支也不再清冻结。
- **遗留**：跳变没了，但**缓慢滑移**浮现——因为相机彻底冻住后，「全流动」造成的**质心平移**无处掩盖，整簇在屏幕上滑走。

### 第 4 轮（真正的节点侧根因）：质心平移 → forceCenter 质心锁
- **现象根因**：见 §5。前 3 轮全在相机侧；这一轮才碰到节点侧。
- **做法**：拖拽期间装 `forceCenter(按下瞬间质心)` 钉住整簇质心；流体只能围绕固定质心局部填补 → 整簇不整体平移 → 图谱稳在中央。主线程 + worker 双实现。生命周期用现有信号兜死（§6.3）。

## 5. 根因总结：两条独立的轴，之前只治了一条

把「视图为什么会动」拆成两条**正交**的轴，问题立刻清晰：

| 轴 | 物理含义 | 拖拽时谁在动它 | 对应的锁 |
|---|---|---|---|
| **缩放 / 包围盒轴** | 归一化跨度 + 中心（zoom & 映射尺度） | 节点流动 + 被拖节点跑远 → 实时包围盒每帧变 | `setCustomBBox` 冻结归一化 |
| **平移轴** | 整簇质心在图坐标里的位置 | 「全流动」解锁全图后，被拖节点钉在远处，链接力把整簇质心拽过去 | `forceCenter` 钉质心 |

**为什么前几轮顾此失彼**：第 1 轮冻住了「缩放/包围盒轴」，主画布不再逐帧跳，于是误以为相机侧治完了；但「平移轴」（质心平移）一直没碰。当相机被彻底冻住后，质心平移失去了 auto-fit 的掩盖，**直接表现为整簇在屏幕上滑走**——也就是第 5 个现象。
**元教训**：当一个「冻结相机」的设计仍然表现出运动时，要去看**是不是节点本身在平移**，而不只是盯着相机。相机冻与不冻救不了质心平移：冻了→图滑走；不冻（auto-fit 跟质心）→就是第 1 轮那种逐帧跳/漂。**必须从节点侧阻止质心平移。**

## 6. 正确的最终方案

### 6.0 方案选型（如何对待 W7 的两条优先级）
为「阻止质心平移」有三档，对应是否保留流体：

| 档 | 拖拽时其余节点 | 流体 | 稳定 | 复杂度 |
|---|---|---|---|---|
| ① 全钉死，只动被拖节点 | 不动 | ❌ | ✅ 最稳 | 最低 |
| ② 只放被拖节点+一跳邻居 | 局部动 | ⚠️ 打折 | ✅ | 中 |
| ③ 保留整图全流动 + `forceCenter` 钉质心 | 全流动 | ✅ 完整 | ✅ | 最高 |

用户明确「流体是对齐 Obsidian 的关键能力、要保留」，故**放弃最省事的 ①**（它会废掉团队之前为实现液体填补而写的「全流动」），选 **③**——保住完整流体，用质心锁补稳定。③ 的全部风险集中在「质心锁何时解除」，靠 §6.3 的现有信号方案兜死，避免再成地鼠洞。

### 6.1 逐事件 × 子系统矩阵（最终行为）

> 这就是用户要求「全局梳理」的产物：把每个事件的「节点线」与「相机线」都列清，确认无一处自相矛盾。

**mouseDown（命中节点）**
- 节点线：① 解锁全部 `fx/fy`（保留全流动）；② 把被拖节点钉到当前位置；③ **计算当前可见节点质心 C0，装 `forceCenter(C0)` 质心锁**；④ `wake(0.3)`。
- 相机线：冻结归一化——`if (!getCustomBBox()) setCustomBBox(getBBox())`（冻结到当前基准，不重捕获，零跳变）。
- `preventDefault + stopPropagation`（capture 阶段）→ 阻断 Sigma 的画布拖拽，使 `downStage` 不触发 → 平移惯性 `useCameraInertia` 在节点拖拽期间**不激活**（确认过：这是节点拖拽不会触发相机平移惯性的原因）。

**mouseDown（空白）**：取消选中；不拦截 → 交给 Sigma 原生画布平移/缩放（W6）。

**mouseMove（过阈值后）**
- 节点线：被拖节点 = `viewportToGraph(光标)` 并 `fx/fy` 钉住（**冻结映射下精确跟手**）；`wake(0.3)` 维持流体。质心锁持续生效，整簇不整体平移。
- 相机线：不动（冻结）。降质：`renderLabels=false`、`collide` 迭代 3→1、`interactingRef=true`（minimap 跳过重绘）。

**mouseUp（拖拽）**
- 节点线：解锁被拖节点；`tileIsolatedNodes` 重铺孤立 + `syncIsolatedToSim` 同步回 d3（防飞散）；`wake(0.3)` 沉降。**质心锁不在这里硬清**——交给 §6.3 在沉降接近静止时自动解除，故沉降期间质心仍被钉住、不会松手后继续滑。
- 相机线：不动（冻结保留，不 refit，W4 无跳变）。

**mouseUp（单击）**：选中 / 双击导航；相机与质心锁都不动（冻结保留）。

**数据变化（ML 重布局 / 筛选 / 重建）**：`setCustomBBox(null)` + `setCentroidLock(null)` → 允许 auto-fit（W1/W7，此时本就该重排）。

### 6.2 两把锁各管一轴、互不干扰
- `setCustomBBox` 管**缩放/包围盒轴**：防止被拖节点跑远把视图 zoom 出去、防止 `nodeExtent` 每帧重算带来的逐帧抖。
- `forceCenter` 管**平移轴**：防止整簇被拽着平移滑出视野。
- 二者缺一不可：只冻相机（无质心锁）→ 整簇滑走；只钉质心（无 customBBox）→ 被拖节点跑远仍会撑大实时包围盒、把视图 zoom 出去 + 逐帧抖。

### 6.3 质心锁的生命周期（用现有信号，不用定时器）
这是「不再顾此失彼」的关键。在 `useSimulation` 的 `onTick` 里：

```
if (!motionMode && sim.alpha() < 0.02 && sim.force('centroidLock')) sim.force('centroidLock', null);
```

- `motionMode`（`setMotionMode` 镜像；worker 侧用 `setCollideIterations` 的 `value===1` 镜像）= 是否正在拖拽移动。
- **拖拽中（含按住鼠标停顿）`motionMode=true` → 绝不解除**：堵死「停顿后再动又滑移」的边界（中途解除会让停顿期间的衰减把锁清掉，之后再动就平移）。
- **松手后 `motionMode=false`、`alpha` 衰减到接近静止（<0.02）时自动解除**：既不需要脆弱的 `setTimeout`，也不会残留一个「幽灵力」去污染之后拖力参数滑块等唤醒（否则调滑块时质心会被钉到旧目标 → 又跳）。
- **ML / 筛选处显式 `setCentroidLock(null)`**：数据变化点不应保留拖拽期的质心约束（ML 会重建模拟、力随之消失；筛选不重建，故显式清）。

> 为什么不用定时器：定时器要么太短（沉降未完就解除 → 松手后滑），要么太长（残留幽灵力污染调参）；而 `motionMode + alpha` 是物理状态本身的信号，天然对齐「该不该解除」。

### 6.4  deliberately 没做的事（及理由）
- **没有**「只动被拖节点、其余全钉死」（方案①）——会废掉用户重视的流体能力（W7）。
- **没有**在松手做 auto-fit / 延迟 refit——Obsidian 拖拽/松手本就不动相机，refit 只会制造跳变。
- **没有** toggle `autoRescale`——`customBBox` 设置时它被完全覆盖，留着 `true` 还能保持 `stagePadding` 恒定（toggle 它本身会引入一次 padding 跳变）。
- **没有**让 minimap 自己算 `forEachNode` min/max——必须与主相机同源（`getCustomBBox() ?? getBBox()`），否则节点一流动 minimap 世界框就抖。

## 7. 原理补遗：forceCenter + 钉住节点的残差行为（为什么密集图稳、小图要宽容差）

`forceCenter` 每 tick 平移所有节点使均值→target，但带 `fx` 的被拖节点会被末尾 `x=fx` 覆盖，所以：

- 误差每 tick 乘约 `1/N` 几何收敛；活跃模拟期间的稳态残差主要由 **`mean(vx)`（速度均值）** 决定。
- **密集图（用户的真实图，数百节点）**：速度均值因大数定律相互抵消 → 残差趋近 0 → 整簇纹丝不动。
- **4 节点 E2E 图**：速度均值抵消不充分 → 残差约 **1~2px**（实测拖 40px 时质心只挪 ~1.4px；无质心锁则 10px+）。

由此导出测试容差的选择：小图**不能**用 `toBeCloseTo(..., 1)`（0.05px）这种紧容差，那是把密集图的正确性强加给小图。改用**绝对容差 4px**：带锁 ~1.4px 通过、无锁 ~10px+ 必挂，两边都有余量。

## 9. 给后续维护者的经验教训

1. **先建心智模型再动手**：`screenPos = matrix(camera) ∘ normalization(graph)`；视图动 = 相机动 ∪ 归一化基准动。不要凭感觉调参。
2. **分清两条正交轴**：缩放/包围盒轴（`customBBox`）与平移轴（`forceCenter`）。一个「冻结相机」方案若仍有运动，先查**节点是否在平移**，别只盯相机。
3. **冻结要冻「相机当前正在用的基准」，别重捕获**：松手持久冻结后，空闲取景基准 ≠ 实时包围盒；重捕获会在按下瞬间切基准 → 跳变。
4. **生命周期优先用物理/状态信号，慎用定时器**：`motionMode + alpha` 对齐「该不该解除」，且要覆盖「按住停顿」边界；定时器要么太短要么残留幽灵力。
5. **API 语义要读源码确认**：`getBBox()` ≠ `getCustomBBox() ?? getBBox()`；前者无视 `customBBox`。minimap 必须与主相机用**同一**基准表达式。
6. **主线程 / worker 双实现**：密集图走 worker，只改主线程等于没修。
7. **测试容差要匹配被测图规模**：物理残差随 N 变化；小图用绝对容差，别用密集图才成立的紧容差。
8. **改动前列「事件 × 子系统」矩阵**（§6.1），逐格确认相机线/节点线无矛盾——这是避免地鼠式返工的最有效手段，也是用户在第 4 轮明确要求「从全局梳理」的原因。
9. **读用户优先级，别替他做产品取舍**：用户说「稳定为根基 + 流体要保留」时，最稳但砍流体的方案（①）反而是错的；正确做法是保留流体、用约束补稳定（③）。

## 11. 后续迭代（路线 B 第二轮）与当前真实状态

> 本章是**当前代码**的准确描述。§6.2 / §6.3 / §7 / §8.3 描述的 `forceCenter` 质心锁 + 松手沉降方案，
> 在本轮已被**推翻**（见 §11.3 原因）；§8 的第 3 条断言也已替换为「包围盒 span 防爆 + 映射冻结」。
> 阅读时请以本章为准。

### 11.1 用户在路线 B 第一轮后的复测反馈（驱动本轮的四条）
1. 拖拽时**避让不明显**——想要"磁铁式引力碰撞"，未接触就让路，而非碰到才动。
2. 位移后**有回弹的引力**（被推开的节点被拽回旧位置）。
3. **孤立节点几乎不动**。
4.（新增）**松手后图谱还在动**，像延迟动画。

### 11.2 当前拖拽模型（逐事件，当前代码）
**mouseDown（命中节点）**：解锁**全部**节点（含孤立）；被拖节点钉到光标；冻结相机（`setCustomBBox`，仅当为空时）；
`beginDrag` = 快照锚点 + 装**三类拴绳** + 装**磁铁排斥场**；`wake`。向心力**保持开启**（平衡态与排斥/边力抵消，对局部气泡影响可忽略，省去 disable/restore 状态切换）。
- 三类拴绳强度 = f(到被拖节点当前距离)，按节点类别分档：
  - 直接邻居 = `NEIGHBOR_TETHER`(0) → 完全自由，靠边力受牵引跟随；
  - 连接非邻居 = 近 `CONN_NEAR`(0)→远 `CONN_FAR`(0.85)：**近端=0 是关键**，被推开后就地停、不弹回旧锚点；
  - 孤立 = 近 `ISO_NEAR`(0.18)→远 `ISO_FAR`(0.6)：中等牵引绳，磁铁近时能被推开、绳子拽住防飞散。
- 磁铁场：以被拖节点为中心、`rMagnet` 为半径，场内（邻居除外）受向外推力 ∝ `(1−dist/rMagnet)²`，未接触即避让。
- 屏幕像素半径（GraphPage，用冻结映射换算成图坐标）：自由区 `DRAG_FLOW_INNER_PX`=170、钉死起始 `DRAG_FLOW_OUTER_PX`=320、磁铁 `DRAG_MAGNET_PX`=210。**自由区 ≥ 磁铁区**，使整个被犁区域拴绳=0 → 无回弹。

**mouseMove（拖拽）**：被拖节点 = 光标图坐标（`fx/fy`）；`wake`；降质（标签关、collide 1 次）。磁铁 + 拴绳每 tick 作用 → 近处避让/流体、邻居牵引、孤立受控反应、远处钉死。

**mouseUp（拖拽 / 单击）**：`endDrag`（撤拴绳 + 磁铁）→ **`freezeAllNow`：把所有可见节点就地钉死（`fx/fy`=当前坐标，graph + d3 同步）+ `simulation.stop()`** → **零后续运动**；恢复标签/collide；`refresh`。
**不**沉降、**不**重铺孤立、**不**装质心锁、**不** `wake`。相机冻结保留。

**数据变化（ML / 筛选 / 重建）**：`setCustomBBox(null)` → auto-fit。
（`setCentroidLock` 基础设施仍留在 `useSimulation`/worker，但拖拽流程已不再调用，属可清理的死代码。）

### 11.3 为什么推翻第一轮的「质心锁 + 松手沉降」
- **回弹（反馈 2）** 的根因是第一轮拴绳的"自由区"太小（70px），真正被犁的那一圈落在拴绳>0 区，被推开后又被拴绳拽回旧锚点。→ 本轮把自由区扩到盖住磁铁区，并让连接近端拴绳=0。
- **松手后还在动（反馈 4）** 的根因是第一轮松手重新开启向心 + `wake` 做沉降，拖拽期被推开的节点在松手后被向心拽回 = 用户看到的"延迟动画"。→ 本轮松手**直接定格**（pin + stop），从根上消除任何回弹/沉降，也顺带让质心锁变得不必要。
- **避让弱（反馈 1）/ 孤立不动（反馈 3）**：第一轮没有磁铁，避让只靠接触式 `forceCollide` + 偏弱的全局排斥；孤立又被硬钉死。→ 本轮加磁铁 + 放开孤立硬钉（改牵引绳）。

### 11.4 仍开放的项：密集图的磁铁"犁感"（诚实记录）
结构已能消除回弹 / 松手动 / 整簇滑移，但**密集图上磁铁犁开人群的观感仍偏弱**（用户复测"差强人意"）。
原因：密集图每个节点被大量边 + 碰撞"焊"得很硬，单个磁铁（即便 `MAGNET_STRENGTH`=2.0）难以明显犁动人群。
**剩余可调旋钮**（`useSimulation.ts` 与 `simulation.worker.ts` 各一份，调时两处一起）：
- `MAGNET_STRENGTH`(2.0) 继续上调；`DRAG_MAGNET_PX`(210) 调影响范围；
- 或在拖拽期**临时降低气泡内的碰撞/边刚度**，让人群更易让路；
- `ISO_NEAR/ISO_FAR` 调孤立反应/防飞平衡；`DRAG_FLOW_INNER_PX/OUTER_PX` 调自由区/滞后带。
**若力模拟调参仍无法满足**，下一步候选是**运动学位移场**（早期路线 A）：直接按"光标移动 × 距离衰减"算每个节点的位移，天然确定性、松手即停、孤立也不会飞（位移按帧有界、非加速）；代价是要自行处理碰撞/级联/滞后，改动较大。**本轮未采用**，因力模拟路线尚未穷尽且运动学重写风险更高。

### 11.5 一个刻意的行为取舍
松手**定格**意味着**不再自动重铺孤立圆环**——多次拖拽后外围孤立点不会归整（会慢慢散），需点**重布局**规整。
这是"消灭松手动画"的必然取舍（重铺=孤立弹回圆环=又是一段动画）。若后续希望"松手后孤立静默归环而不产生可见动画"，需单独设计（例如归环但不唤醒渲染帧的渐进过渡），本轮未做。
